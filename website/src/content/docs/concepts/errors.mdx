Errors cross three boundaries: from the domain to the use case, from the use case to a transport, and from the transport to a client. Two rules keep that safe and readable:

1. **Every layer shares five kinds,** so a store, a use case and a handler agree on what "not found" means without importing each other.
2. **What a client reads is set on purpose.** Wrapped context is for logs. A message reaches a client only when the code says it may.

## One table, one place

Each transport maps kinds to its own codes in one table: `httpx` for HTTP, `connectx` for Connect. Handlers never pick a status code for an error themselves.

| Error | HTTP status |
|---|---|
| `*apperr.ValidationError`, `apperr.ErrInvalid` | `400`, with `errors` set for a validation error |
| `*http.MaxBytesError` | `413` |
| `*httpx.TooManyRequestsError` | `429`, with `Retry-After` in seconds |
| `apperr.ErrUnauthorized` | `401`, with `WWW-Authenticate: Bearer` |
| `apperr.ErrForbidden` | `403` |
| `apperr.ErrNotFound` | `404` |
| `apperr.ErrConflict` | `409` |
| `context.DeadlineExceeded` | `503` |
| `context.Canceled` | nothing is written: the client left |
| anything else | `500`, with no detail; the error text goes to the log |

Over Connect, `connectx.Errors` sends the same client-safe message with these codes:

| Error | Connect code |
|---|---|
| `apperr.ErrInvalid` | `invalid_argument` |
| `apperr.ErrUnauthorized` | `unauthenticated` |
| `apperr.ErrForbidden` | `permission_denied` |
| `apperr.ErrNotFound` | `not_found` |
| `apperr.ErrConflict` | `aborted` |
| `context.DeadlineExceeded` | `deadline_exceeded` |
| `context.Canceled` | `canceled` |
| anything else | `internal`, with no message |

On the calling side, `connectx.FromConnect` turns the codes back into kinds, and reads `already_exists` as a conflict too.

## Problem details

HTTP errors are RFC 9457 `application/problem+json`, as both OpenAPI documents describe them:

<Code {...problemSchema} />

Confirming an email change to an address another account took meanwhile answers:

```json
{
  "type": "about:blank",
  "title": "Conflict",
  "status": 409,
  "detail": "This email address belongs to another account.",
  "instance": "/v1/me/email-change/confirm",
  "request_id": "0192c1b5-7f3e-7a51-9d2c-4b1f3e8a6c10"
}
```

- `title` is the status text. `detail` is the client-safe message, omitted when there is none.
- `request_id` matches the `X-Request-Id` response header and the request's log line, so a user's bug report leads straight to the logs.
- A validation error adds `errors`, an object from field name to problem.
- A `5xx` never carries `err.Error()`. It might hold a SQL query, a hostname or worse.

The OAuth endpoints are the one exception. `/oauth/token` and `/oauth/revoke` answer in the RFC 6749 shape, `{"error", "error_description"}`, because that is what OAuth clients parse.

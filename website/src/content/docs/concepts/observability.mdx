Everything here uses the standard library and OpenTelemetry. There is no vendor SDK to swap out: point the OTLP exporter at whatever backend you run.

## Logs

Both services log JSON lines with `log/slog`. Each line inside a request carries `request_id`, and `trace_id` and `span_id` when a trace is active, so you can go from a log line to its trace and back.

- `LOG_LEVEL` sets the level (`debug`, `info`, `warn`, `error`; default `info`).
- `LOG_FORMAT` is `json` (default) or `text`, which is easier to read in a terminal.

Every HTTP request gets one line, `request`, with `method`, `pattern`, `status`, `bytes`, `duration` and the request ID, plus `err` when the handler failed. A `5xx` logs at error level, and a client that left before the response at debug. The route pattern, such as `/v1/clients/{id}`, is logged instead of the raw path, so IDs in paths don't explode your log index. The gateway's access log keeps the path without its query string, so the sign-in codes in mailed links stay out of it.

**Request IDs.** An incoming `X-Request-Id` is kept if it is 1 to 64 characters of letters, digits, `.`, `_` or `-`. Otherwise the service makes a new one. Either way it is echoed in the response and in every problem body.

**Redaction.** The handler replaces the values of keys that hold credentials with `[redacted]`: `password`, `secret`, `token`, `access_token`, `refresh_token`, `authorization`, `cookie`, `set-cookie`, `client_secret`, `code` and `code_verifier`. Secrets in config use a `Secret` type that prints `[redacted]` too.

## Traces and metrics

When `OTEL_EXPORTER_OTLP_ENDPOINT` is set, or one of its per-signal variants, the services export traces and metrics over OTLP/HTTP. When it isn't, the providers are no-ops and cost nothing. These are the OpenTelemetry SDK's standard variables, so any collector works.

Incoming HTTP requests get a span named after the method and route, such as `GET /v1/clients/{id}`. Trace context propagates with the W3C `traceparent` header and baggage.

## Health probes

| Route | Answers |
|---|---|
| `/livez` | `200` while the process runs. |
| `/readyz` | `200` when every readiness check passes and the service isn't shutting down. Otherwise `503`, with a problem body naming the checks that failed or saying the service is draining. A check's error is logged, not sent. |

The readiness checks cover what the service needs to serve, such as its database. Kubernetes probes these routes; compose runs `<service> healthcheck`, which asks the local `/readyz`, because the distroless image has no shell or curl.

## Shutdown

On `SIGINT` or `SIGTERM` a service:

1. flips `/readyz` to `503`, so load balancers stop sending it traffic;
2. waits `SHUTDOWN_DELAY` (default `5s`) for them to notice;
3. shuts down every server and worker concurrently, allowing `SHUTDOWN_TIMEOUT` (default `20s`) for requests in flight to finish;
4. exits non-zero if anything failed to stop cleanly.
